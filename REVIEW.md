# Правила код-ревью

Правила для ревью изменений в Cash Tracker. Источник истины — [CLAUDE.md](CLAUDE.md), [backend/CLAUDE.md](backend/CLAUDE.md), [frontend/CLAUDE.md](frontend/CLAUDE.md) и [README.md](README.md). При расхождении прав CLAUDE.md. Ответы и комментарии ревью пишутся по-русски.

## Как оформлять замечания

- Каждое замечание: файл и строка, в чём проблема, что сломается, как исправить.
- Уровни:
  - **Блокер** — ошибка, утечка данных пользователя, нарушение контракта API, падающие проверки. PR не сливается.
  - **Важно** — нарушение правил проекта, нет теста, ломкий код. Исправить до слияния.
  - **Замечание** — мелочи и стиль. Можно оставить на усмотрение автора.
- Проверяйте то, что реально изменилось: `git diff main...HEAD` и `git log main..HEAD`. Не предлагайте попутный рефакторинг и новые зависимости без необходимости.

## Чек-лист для ревьюера

Пройдите по пунктам перед тем, как оставить вердикт.

- [ ] Прочитал описание PR и сверил его с реальным диффом (`git diff main...HEAD`, `git log main..HEAD`).
- [ ] Заголовок PR и коммиты оформлены по Conventional Commits, нет подписей инструментов.
- [ ] Ветка создана от актуальной `main` и содержит одну задачу, нет несвязанных правок.
- [ ] Данные пользователя изолированы: чужая запись даёт 404, `user_id` не берётся из запроса.
- [ ] Суммы в разных валютах не складываются и не конвертируются.
- [ ] Контракт API изменён — обновлены README, тесты бэкенда и `frontend/src/types/api.ts`.
- [ ] Для новой логики и исправлений есть тесты; для исправления ошибки — тест, который её воспроизводит.
- [ ] Тесты бэкенда и фронтенда, линтеры, проверка типов и Prettier проходят (или в PR сказано, что не запускались).
- [ ] Миграции не правят уже применённые, есть `safeDown`, схема вынесена в отдельный коммит `db`.
- [ ] Нет секретов, `.env` и файлов из `.gitignore`.
- [ ] Тексты, комментарии и сообщения об ошибках — по-русски, идентификаторы — по-английски.
- [ ] Выполненные шаги отмечены в `.claude/plans/cash-tracker-plan.md`.
- [ ] Каждое замечание имеет уровень (блокер, важно, замечание) и указание, как исправить.

## Пропускать

Эти файлы не разбирайте построчно: они генерируются или не содержат логики проекта.

- Lock-файлы: `backend/composer.lock`, `frontend/package-lock.json` и любые `*.lock`. Смотрите только, что вместе с ними изменён `composer.json` или `package.json`, и что в `package.json` / `composer.json` нет неожиданных новых зависимостей.
- Сборка и сгенерированный код: `dist/`, `coverage/`, `*.min.js`, `*.min.css`, `*.map`.
- Установленные зависимости: `node_modules/`, `vendor/`. В диффе их быть не должно, а если есть, это замечание к PR.
- Бинарные файлы и изображения: `*.png`, `*.jpg`, `*.ico`, `*.svg`, шрифты.
- Автоматически создаваемые файлы: `frontend/env.d.ts`, снимки тестов `*.snap`.
- Только форматирование: правки пробелов и переносов строк, которые делает Prettier, без смены кода.

Но не пропускайте, даже если файл похож на служебный:

- `.env.example`, `docker/` и `docker-compose.yml`: там описаны переменные окружения и конфигурация окружения.
- `backend/migrations/`: даже сгенерированный командой `yii migrate/create` файл содержит схему БД.
- `README.md`, `CLAUDE.md` и `REVIEW.md`: документация и правила проекта, в том числе описание API.

## Общие проверки (весь репозиторий)

1. **Изоляция данных.** Чужая запись неотличима от несуществующей (404, не 403). `user_id` не принимается из запроса и не попадает в ответ.
2. **Валюты.** Суммы в разных валютах не складываются и не конвертируются. Отчёты и бюджеты разбиты по валюте счёта.
3. **Контракт API.** Изменён endpoint или формат ответа — в том же PR обновлены README (раздел «API»), тесты бэкенда и `frontend/src/types/api.ts`. Если старые клиенты перестают работать, в заголовке `!` и в описании раздел «Ломающие изменения».
4. **Секреты.** В диффе нет `.env`, паролей, ключей и токенов. Новые переменные окружения описаны в `.env.example` и README.
5. **Язык.** Комментарии, сообщения об ошибках и тексты интерфейса — по-русски. Идентификаторы, имена файлов и веток — латиницей.
6. **Объём.** Изменение делает только то, что заявлено в задаче. Нет несвязанных правок, лишних файлов, закомментированного кода.
7. **Тесты.** Новая функциональность и исправления сопровождаются тестами. Исправление ошибки включает тест, который её воспроизводит.
8. **План работ.** Выполненные шаги отмечены в `.claude/plans/cash-tracker-plan.md`.
9. **Мусор в диффе.** Нет `node_modules`, `vendor`, `dist`, `coverage` и других файлов из `.gitignore`.

## Бэкенд (`backend/`, Yii2)

- Контроллеры ресурсов наследуют `OwnedActiveController`. Особенности ресурса задаются в `sortConfig()`, `assertDeletable()` и подобных методах, действия не переписываются.
- Модель с `user_id` использует `OwnedByUserTrait`. Все выборки идут только по данным текущего пользователя.
- Ошибки — исключения Yii (`NotFoundHttpException`, `ConflictHttpException` и т. д.). Свой формат ответа об ошибке в контроллерах не делается. В `prod` в ответе нет поля `debug`.
- Суммы — `numeric(14,2)`, наружу строкой с двумя знаками (`"1234.50"`), без приведения к `float`. Даты — `ГГГГ-ММ-ДД`, месяцы — `ГГГГ-ММ`.
- Запросы собираются через Query Builder с параметрами. Пользовательский ввод не конкатенируется в SQL. Фильтры и сортировка — по белым спискам полей.
- Ограничения целостности (`unique`, внешние ключи, `CHECK`) заданы и в миграции, и в правилах валидации модели.
- Новые endpoint-ы зарегистрированы в `config/web.php` и описаны в README.
- Миграции:
  - имя `mYYMMDD_HHMMSS_описание`, создана через `yii migrate/create`;
  - применённые и попавшие в `main` миграции не изменены, правка — новой миграцией;
  - есть `safeDown` (или `down`);
  - изменение схемы вынесено в отдельный коммит с областью `db`.
- Тесты: каждый endpoint покрыт в `tests/Api/*Cest.php` (успех, 401, 404 для чужой записи, 422, граничные случаи); логика моделей и расчётов — в `tests/Unit`. `codecept run` проходит целиком.

## Фронтенд (`frontend/`, Vue 3)

- Только `<script setup lang="ts">`, строгие типы, без `any`. Типы API лежат в `src/types/api.ts` и соответствуют контракту.
- Запросы к API — только через функции из `src/api/`, не напрямую из компонентов. Ошибки разбираются через `toApiError`: 422 показывается у полей, остальные — сообщением в форме.
- Состояние данных (списки, загрузка, ошибки) живёт в Pinia-хранилищах. Локальное состояние формы и диалога остаётся в компоненте.
- UI собран из компонентов PrimeVue и токенов темы (`var(--p-...)`), без жёстко заданных цветов; светлая и тёмная темы работают. Стили — `<style scoped>`.
- Суммы приходят строками, форматируются только через `src/utils/format.ts`, суммы в разных валютах не складываются.
- Логика обработки 401 остаётся в `http.ts` и не дублируется. Токен хранится в `localStorage`.
- Новая страница: компонент в `views/` (`*View.vue`), маршрут в `router/index.ts` с `meta.title` (и `requiresAuth` или `guestOnly` при необходимости), пункт меню в `layouts/AppLayout.vue`.
- Не дублируется то, что уже есть в `utils/`.
- Компоненты называются в PascalCase, импорты идут через алиас `@/`.
- Prettier: без точек с запятой, одинарные кавычки, ширина строки 100.
- Тесты: новый компонент, хранилище и функция в `api/` или `utils/` получают `*.spec.ts` в `__tests__/`. HTTP мокается. Тесты проверяют поведение, а не детали реализации.

## Коммиты, ветки и pull request

- Коммиты по Conventional Commits: `<тип>(<область>): <описание>`. Тип латиницей, описание по-русски, в нижнем регистре, без точки, вся строка до 72 символов. Области: `backend`, `frontend`, `api`, `docker`, `db`, `docs`.
- Один коммит — одно логическое изменение. Тело коммита объясняет, что и зачем, строки до 72 символов.
- В коммитах и описании PR нет `Co-Authored-By`, `Signed-off-by` от инструментов и подписей вроде «Generated with …».
- Нет `--no-verify`, переписывания отправленной истории и прямых коммитов в `main`.
- Ветка создана от актуальной `main`, называется `<префикс>/<краткое-описание>` (`feature`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`), содержит одну задачу.
- Заголовок PR оформлен как коммит. Описание содержит разделы: «Что сделано», «API», «Ломающие изменения» (если есть), «Как проверить», «Заметки для ревьюера». Описание соответствует реальному диффу.
- Перед слиянием проходят все проверки:
  - бэкенд: `docker compose exec php php vendor/bin/codecept run`;
  - фронтенд: `npm run test`, `npm run lint`, `npm run type-check`, `npx prettier --check .`, `npm run build`.
  Если проверка не запускалась, об этом сказано в PR.
- Слияние — squash merge. После него ветка удаляется локально и на удалённом репозитории.
