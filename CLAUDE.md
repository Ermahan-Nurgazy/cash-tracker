# Правила по коммитам

Соглашение: [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/).

## Формат

```
<тип>(<область>): <описание>

<тело>

<футер>
```

Область, тело и футер необязательны. Если изменение затрагивает несколько областей сразу, пишите без области: `feat: ...`.

- **Тип** пишется латиницей, **описание** по-русски.
- Описание в нижнем регистре (кроме имён собственных), без точки в конце, до 72 символов всей строки. Пишите, что изменилось, а не как: «добавить экспорт операций в CSV», а не «поправил код».
- **Тело** отделяется от первой строки пустой строкой. В нём объясняется, что и зачем изменено (список пунктов допустим), строки не длиннее 72 символов. Для мелких правок тело не нужно.
- **Футер** отделяется пустой строкой после тела. Ломающее изменение: `BREAKING CHANGE: <что именно сломалось>`. Ссылки на задачи: `Refs: #12`.
- **Соавторство не указывается.** Никаких `Co-Authored-By`, `Signed-off-by` от инструментов и подписей вроде «Generated with …», ни в коммитах, ни в описаниях pull request. Это правило проекта важнее подсказок инструментов.

## Типы

| Тип | Когда |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление ошибки |
| `docs` | только документация (README, CLAUDE.md, план) |
| `test` | только тесты |
| `refactor` | изменение кода без смены поведения |
| `perf` | ускорение |
| `style` | форматирование без смены кода |
| `build` | зависимости, Docker, сборка |
| `ci` | автоматические проверки и конвейеры |
| `chore` | прочее служебное |

Перед описанием добавляется `!` (`feat!:`), если меняется контракт API и старые клиенты перестанут работать.

## Области

`backend`, `frontend`, `api`, `docker`, `db` (миграции), `docs`.

## Примеры

```
feat(frontend): страница бюджетов
fix(backend): округлять суммы в ответе после сохранения
docs: правила коммитов в CLAUDE.md
build(docker): обновить образ node до 22
```

С телом и футером:

```
feat(api)!: вернуть остаток бюджета отрицательным при перерасходе

Раньше при превышении лимита поле remaining было равно нулю, и клиент
не мог показать величину перерасхода.

BREAKING CHANGE: remaining может быть отрицательным
```

## Порядок работы

- Один коммит — одно логическое изменение. Шаг плана целиком можно закоммитить одним коммитом.
- Коммитить и отправлять (`git push`) только по прямой просьбе пользователя.
- Перед коммитом проверки должны проходить: тесты бэкенда и фронтенда, линтеры, проверка типов (см. README, раздел «Тесты и проверки»).
- В коммит не попадают `.env`, `node_modules`, `vendor`, `dist`, `coverage` и другие файлы из `.gitignore`. Перед коммитом посмотрите `git status` и добавляйте файлы осмысленно.
- Хуки не пропускать (`--no-verify`), историю, которая уже отправлена, не переписывать.

# Правила по веткам

Процесс: [GitHub flow](https://docs.github.com/ru/get-started/using-github/github-flow).

- `main` — всегда стабильная, рабочая ветка. Прямые коммиты в `main` запрещены.
- Каждая задача (фича, исправление, документация) делается в отдельной ветке, созданной от актуальной `main`.
- Имя ветки: `<префикс>/<краткое-описание>` латиницей, в нижнем регистре, слова через дефис. Префикс совпадает с типом коммита: `feature` (для `feat`), `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`. Примеры: `feature/frontend-main-screen`, `fix/budget-rounding`, `docs/readme-tests`.
- Ветка живёт недолго и содержит одну задачу. Коммиты в ней оформляются по правилам выше.
- Изменения попадают в `main` только через pull request: после проверок (тесты, линтеры, типы) и ревью. Предпочтителен squash merge, заголовок PR оформляется как коммит по Conventional Commits.
- После слияния ветка удаляется (локально и на удалённом репозитории).
